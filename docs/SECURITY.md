# PULSE-010 — безопасность входа и административных сессий

Реализация для экспериментальной ветки v0.2.0:

- Пять неуспешных попыток за 15 минут блокируют дальнейший вход с источника.
- При блокировке сервер возвращает HTTP 429 и `Retry-After`.
- Счётчик хранится в SQLite; адрес источника не сохраняется в открытом виде.
- При успешном входе неуспешные попытки этого источника очищаются.
- Административные сессии хранятся сервером в виде SHA-256 от случайного токена.
- Выход из системы отзывает сессию даже при повторном предъявлении cookie.
- Срок действия административной сессии — 4 часа.
- Добавлены CSP, `Referrer-Policy: no-referrer`, `X-Frame-Options`,
  `X-Content-Type-Options` и `Cache-Control: no-store` на личных страницах.
- Удалён inline JavaScript обработчик в карточке сотрудника.
- Добавлена миграция Alembic `20261111_0002`; на VPS пока не применять.

## Доверие IP за Caddy

В отсутствие `PULSE_TRUSTED_PROXY_CIDRS` приложение игнорирует клиентский
`X-Forwarded-For` и считает источником непосредственного TCP-peer.
Это исключает подмену IP заголовком, но за Caddy приводит к одному общему
rate-limit bucket: все внешние посетители могут блокировать друг друга.

До допуска в production необходимо:
1. Узнать точную подсеть, из которой Caddy подключается к ПУЛЬС.
2. Закрепить предсказуемый CIDR доверенной edge-сети или иной надёжный peer.
3. Настроить `PULSE_TRUSTED_PROXY_CIDRS` только для этой подсети.
4. Проверить, что reverse proxy самостоятельно формирует X-Forwarded-For,
   а внешние клиенты не могут подсунуть произвольный заголовок.
5. Пройти тест прямого соединения и тест spoofing.

Нельзя указывать `0.0.0.0/0` или доверять любым proxy headers.

## Операционный контроль

После смены `ADMIN_PASSWORD` действующие сессии отзываются
через отдельную административную команду (см. ниже).
Также действует индивидуальный отзыв при logout и истечение срока жизни.

## Массовый отзыв сессий после смены пароля

В v0.2.0 предусмотрена отдельная административная команда:

```bash
python -m scripts.revoke_admin_sessions \
  --database-url sqlite:///./pulse.sqlite3 \
  --confirm-revoke-all
```

Команда не читает и не выводит пароли, отзывает только действующие
административные сессии и возвращает их количество. После отзыва
старые cookie не дают доступ, даже если они сохранены в браузере.

В production команду разрешено выполнять только после резервного
копирования, проверки миграции схемы и отдельного решения по релизу.
Смена пароля сама по себе **не** отзывает сессии — эту команду нужно
включить в процедуру смены доступа.

Устаревшие записи неудачных входов удаляются при следующей
регистрации ошибки; общий журнал попыток не растёт безгранично.

## PULSE-010: проверка доверенного прокси (11.11.2026)

Read-only аудит VPS показал: `pulse_public_edge=172.20.0.0/16`,
Caddy `172.20.0.3`, ПУЛЬС `172.20.0.2`. Для production
предназначен **один** доверенный IP: `172.20.0.3/32`.

В Dockerfile Uvicorn запускается с `--no-proxy-headers`.
В приложении идентификация HTTP peer выполняется независимо от заголовков,
после чего допускается ровно один IP в `X-Forwarded-For` только от
`172.20.0.3/32`. Цепочка адресов, поддельный IP или запрос
не от Caddy игнорируются. Конфигурация с `/16` или `/0` отклоняется
при инициализации приложения.

Caddy по умолчанию игнорирует недоверенные входящие `X-Forwarded-*`;
это поведение нужно проверить именно на реальном Caddyfile перед RC.

**Критический эксплуатационный инвариант:** адрес Caddy закрепляется
в отдельном Compose-проекте сайта через `ipv4_address: 172.20.0.3`.
Без статического адреса после recreate Caddy может перестать считаться
доверенным, а все внешние входы попадут в общий rate-limit bucket.
Не менять `.env` действующего v0.1.0, не применять новые Compose на VPS
до тестирования изолированной сети.

После восстановления Caddy из исходной конфигурации проверить:
1. Его IP остаётся `172.20.0.3` после recreate.
2. Два браузера с разными клиентскими IP имеют независимые лимиты.
3. Внешний `X-Forwarded-For` нельзя подменить.
4. Прямое обращение к backend с подставленным заголовком не доверяется.
